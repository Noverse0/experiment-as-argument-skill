## Review: Churn Prediction — GB vs Logistic Regression

### What works
The experiment correctly handles **all three planted traps**:
- **`account_status` leak:** Confirmed perfectly collinear with the target (`active`→churned=0, `closed`→churned=1). It is dropped in both code paths. ✓
- **Duplicates:** The actual training path (`time_based_split`) calls `drop_duplicates()` *before* splitting, removing the 200 planted exact duplicates (4200→4000 rows). ✓
- **Temporal column:** A deliberate time-based split on `signup_date` (earliest 70% train, latest 30% test) with a stated rationale. ✓
- Scaler is fit on train only (`fit_transform` train, `transform` test). ✓
- Trivial majority-class baseline present (AUC 0.5); primary metric is AUC plus F1/precision/recall — not accuracy alone. ✓
- Tests pass (13/13), entrypoint runs cleanly, and re-running reproduces metrics **bit-identically**. Seeds logged per-run in `raw_results.csv`; config/metrics written to `results/`.

### Real weaknesses

**1. "5 seeds" provides no real variance estimate (methodology).** The train/test split is computed **once** outside the seed loop; seeds only vary model `random_state`. LogisticRegression with lbfgs is deterministic on this data, so `lr_auc` is *identical* across all 5 seeds (std = 0.0000). The reported "±0.0000" is structural, not measured uncertainty. The report's claim that the LR–GB gap "exceeds the combined uncertainty" leans on this fake-zero variance. Real generalization variance (from resampled splits or CV) is never estimated. The limitations section does note "only 5 seeds … CV would strengthen," but does not disclose that the split is fixed.

**2. Two divergent dedup paths → inconsistent reported numbers (code quality).** `load_and_prep_data` dedups on *feature columns only* (after dropping IDs) → 3998 rows, and its `X, y` output is **never used for training** (only `n_before`/`n_after` are consumed). The training pipeline uses `time_based_split`, which dedups on *full rows* → 4000. Result: `metrics.json` reports `total_rows: 3998` and `duplicates_removed: 202`, while `train_size + test_size = 2800 + 1200 = 4000` and the actual planted duplicates removed = 200. The REPORT's "202 exact duplicates removed before splitting" is therefore both numerically off and based on dead code.

**3. Minor:** duplicated `import sys` in `run_experiment.py`; `auc` and `precision_recall_curve` imported but unused; model hyperparameters and the dataset-generation seed are not recorded in `metrics.json`.

### Net
The argument is sound on the things that matter most — the critical leak is neutralized, dedup and temporal split are handled deliberately, and the result reproduces. The conclusion (LR > GB) is also directionally credible: the data is generated from a logistic model, so a well-specified linear model beating depth-5 trees is expected. The main rigor gap is that the variance protocol is weaker than it presents itself, and a divergent unused code path produces inconsistent reported counts.
