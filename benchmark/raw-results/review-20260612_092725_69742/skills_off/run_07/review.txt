## Review: Churn Prediction Experiment (GB vs LR)

I inventoried the project, read all source/tests/report, ran the test suite (15 passed), ran the entrypoint (~5.5s), and confirmed a byte-identical re-run.

### Leakage — strong
This is the cleanest dimension. The planted traps are all handled deliberately:
- **`account_status` excluded.** `extract_features` selects only `tenure_months, monthly_spend, support_tickets, days_since_signup` — the target-derived `account_status` never enters the model. `validate_no_leak` also detects and logs the leak.
- **Scaler fit on train only.** `scale_features` does `fit_transform` on train, `transform` on test (`src/preprocessing.py:98-100`).
- **Dedup before split.** `remove_duplicates` runs in `prepare_data` before `time_based_split`, so the 200 exact duplicates can't straddle the split.
- **Temporal column handled deliberately.** A genuine time-based split at the 75th percentile of `days_since_signup`, justified in the report.
- A **label-shuffle** sanity check is present and passes at runtime (0.44 vs 0.50 baseline).

### Methodology — adequate with a real weakness
Trivial baseline present (stratified `DummyClassifier`, ROC-AUC ≈ 0.50). Metrics are appropriate for imbalance (ROC-AUC + precision/recall/F1, not accuracy alone). Neither model is tuned, so the "same budget" condition is trivially satisfied. **But the "5 trials per model" is mostly illusory:** `LogisticRegression` uses the default `lbfgs` solver, which is deterministic — `random_state` does nothing, so all 5 LR trials are identical and `std = 0.0`. GB's tiny variance comes only from `subsample=0.8` on a **single fixed split**. There is no cross-validation or multi-split resampling, so the reported variance does not estimate the uncertainty that actually matters (split variability).

### Reproducibility — strong
Seeds fixed (data seed 7; trial seeds 42–46), metrics written to `results/metrics.json`, config echoed into the report. Re-running produced a byte-identical `REPORT.md` and `metrics.json` (`git status` clean afterward).

### Claims discipline — the weakest dimension
Two problems:
1. **The report asserts a result the code measured as false.** The "Sanity Checks" section of the generated report **hardcodes** `✓ Overfit Tiny Batch: Model achieves ROC-AUC > 0.95` (`run_experiment.py:97-99`), independent of the actual outcome. At runtime the overfit check **failed** (ROC-AUC 0.7867 < 0.95) and the program even printed *"Some sanity checks failed. Results may not be reliable."* — yet the report claims a clean pass.
2. **"Confidence intervals do not overlap, suggesting the difference is real" overclaims.** This rests on LR's `std = 0.0` (an artifact of determinism) and single-split model-seed jitter, not on any resampling of the data.

Credit where due: the team kept the original (refuted) hypothesis and honestly reported that LR won, and the limitations section is candid.

### Executability — strong
`pytest` → 15 passed; `python run_experiment.py` completes in ~5.5s and regenerates outputs deterministically.

### Code quality — good
Readable, modular, dependencies declared and used. Minor issues: `validate_no_leak`'s return value is discarded in `prepare_data`, and the report template's sanity-check block is disconnected from the actual check results (the root of the false claim above).
