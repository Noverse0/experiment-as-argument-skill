## Review: Churn Prediction Experiment

### What was tested
A comparison of Logistic Regression vs. Gradient Boosting on a synthetic churn dataset (4,200 rows + 200 appended duplicates) carrying three planted rigor traps: a target-derived `account_status` leak, duplicate rows that can straddle a random split, and a temporal `signup_date` column.

### Leakage prevention — strong
- **Critical leak caught.** `account_status` (perfectly `closed → churned`) is detected by `hunt_leakage` and dropped by default (`use_leaky_features=False`). This is the headline trap and it was handled correctly (`src/preprocessing.py:65-66`).
- **Transform fitted on train only.** `StandardScaler` is `fit_transform`-ed on train, `transform`-ed on test (`src/preprocessing.py:89-91`). Correct ordering.
- **Temporal column handled deliberately.** A time-based split sorts by `signup_date` and cuts at the 80% index (`src/preprocessing.py:74-82`), with an explicit rationale in the report. Good.
- **Duplicates: detected but not handled.** `check_duplicates` counts 400 duplicate rows and the report checkmarks "Duplicates: Checked before splitting" — but they are never removed. I verified that in this particular split **0 duplicate pairs straddle train/test**, because the time-based sort happens to keep identical-date copies on the same side. So no actual train/test contamination materialized — but by luck of the split, not by intent. The checkmark overstates what the code does.

### Methodological validity — weakened by illusory replication
- Trivial majority-class baseline present (`get_baseline_prediction`); both models beat it.
- Metrics appropriate for the ~27% imbalance: ROC-AUC primary, plus F1/precision/recall (not accuracy alone).
- Neither model is tuned — equal (zero) budget, which is fair, and acknowledged.
- **Core flaw: the "3 independent runs" produce no real variance.** The time-based split is deterministic and identical for every seed, and Logistic Regression is deterministic — so LR's ROC-AUC is byte-identical across all three seeds (std ≈ 1e-16). Only Gradient Boosting's internal randomness varies, by ±0.0003. The seeds therefore do **not** re-split as the report claims; there is effectively one experiment, not three. The 0.038 gap is reported without any significance test, and the near-zero std should have been flagged as an anomaly rather than presented as confirming stability.

### Reproducibility — excellent
Seeds fixed and logged in config and `results.json`; config + metrics + report written to the output dir. Re-running the entrypoint reproduced the committed `results_final` comparison **identically** (verified).

### Claims discipline — mixed
- The dynamically generated Conclusion correctly reports **Logistic Regression wins** (the code follows the data).
- But the hardcoded **Claim** at the top of the report still asserts "Gradient Boosting outperforms Logistic Regression" (`run_experiment.py:26`), directly contradicting its own conclusion — a leftover hypothesis never reconciled.
- The report claims "3 independent runs with variance reported," which misrepresents the deterministic split. Limitations are otherwise honest (small data, defaults, no tuning, distribution shift).

### Executability — excellent
`pytest` → 19 passed in ~2.4s. `python run_experiment.py` completes in seconds and reproduces the committed numbers. Commands work from a clean state.

### Code quality — good
Clean modular structure, dependencies declared and used. Minor dead code: `crosstab` computed but never used (`src/preprocessing.py:33`); `use_leaky_features` is always `False`; returned `scaler` is unused.
