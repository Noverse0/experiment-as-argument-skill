## Review

I inventoried all files, ran the test suite (16 passed), and ran the entrypoint end-to-end (reproduced `results/metrics.json` byte-for-byte). Findings below.

### Leakage prevention — strong
- **`account_status` correctly dropped.** Listed in `DROP_COLS` (`src/pipeline.py:22`), and there's a defensive guard `check_no_leakage_columns` that *raises* if it survives (`src/sanity.py:47`), plus a unit test for the raise path. This is the planted critical leak and it's handled cleanly.
- **Fit-transforms are train-only.** `StandardScaler` lives inside the `Pipeline` and is fit via `pipe.fit(X_train, ...)` — no fitting on full data. (GB has no scaler, which is correct: trees are scale-invariant.)
- **Dedup before split.** `drop_duplicates()` runs in `load_and_clean` before `temporal_split`; the 200 planted exact duplicates are removed (4200→4000, confirmed in run output). No rows straddle the split.
- **Temporal column handled deliberately** — time-ordered 80/20 split, justified in docstring and report.
- **Residual concern (undiagnosed):** `signup_day` is kept as a feature *and* the split is temporal, so every test `signup_day` lies outside the train range. Trees can't extrapolate, which plausibly explains GB collapsing to chance (AUC 0.509, accuracy 0.42 — below the majority baseline). The label-shuffle sanity check fires (AUC 0.609 > 0.6, "possible leakage"), and the report surfaces the warning honestly but never investigates its cause. No critical leak remains, but this interaction is the real story behind the numbers and goes unexamined.

### Methodology — adequate, one soft spot
- Trivial baseline present (majority-class `DummyClassifier`, AUC 0.50). ✓
- Metrics appropriate for ~27% positive rate: ROC-AUC primary plus F1/precision/recall, not accuracy alone. ✓
- Equal tuning budget (both untuned, stated honestly). ✓
- **Variance methodology is partly theater.** LR is deterministic on a fixed split, so its 3 seeds produce identical numbers (std = 0.0) — three copies of one run, zero information. The `noise_threshold = max(std)` therefore reflects only GB's seed jitter and ignores the dominant uncertainty (train/test split variance). The "winner requires gap > noise" rule looks rigorous but rests on an uncertainty estimate that excludes the main source. The report's Limitations do acknowledge this.

### Reproducibility — strong
Seeds fixed and logged (`SEEDS=[42,7,123]`), full config+metrics written to `results/metrics.json`, dataset generation deterministic. Re-running produced an identical metrics file.

### Claims discipline — mostly honest, mild over-headline
Limitations are thorough and candid (single split, fixed HP, 3-seed lower bound, synthetic data). Sanity warnings (overfit FAIL, shuffle leak) are reported, not buried. All report numbers trace to measured values. The deduction: the bold "**Logistic Regression Wins**" headline interprets a GB model that performs *below the trivial baseline* as "LR is the better churn model," when the honest reading is "GB is broken by the temporal-feature/extrapolation setup." Declaring a definitive winner from one split with a near-zero noise threshold slightly overstates confidence.

### Executability — excellent
`pytest` → 16 passed in 2.65s. `python3 run_experiment.py` → completed in ~5s, wrote metrics and REPORT.md. Dependencies declared in `requirements.txt` and all used.

### Code quality — clean
Typed, well-documented, modular (pipeline/experiment/sanity split), no dead code. Minor: `write_report` hardcodes the literal `4200` to back out the dup count (`run_experiment.py:60`) rather than recording original row count — brittle if `n` changes.
