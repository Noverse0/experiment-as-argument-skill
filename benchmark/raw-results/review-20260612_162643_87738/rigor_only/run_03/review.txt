- **`account_status` dropped** in `engineer_features` (the critical leak). Verified it's a pure target encoding; correctly excluded.
- **`customer_id` dropped** as opaque identifier.
- **Duplicates removed before splitting** (`dedup` runs prior to `time_split`), so the 200 exact dups cannot straddle the split. This is the correct ordering.
- **Scaler fit on train only** (`fit_transform(X_train)`, `transform(X_test)`) — no test contamination.
- **Temporal split is deliberate**: sorted by `signup_date`→`days_since_start`, earliest 80% train. Justified explicitly in code and report.
- Minor: `days_since_start` is both the split key *and* a feature, so its test range lies entirely outside the train range (extrapolation). Acknowledged as non-predictive in the report, so low impact. Date ties at the cutoff could place same-day customers on both sides, but that's not row-level leakage.

### Methodology — strong, with one structural limit
- Trivial baseline present (`DummyClassifier` majority-class, 0.75).
- Metrics appropriate for imbalance: ROC-AUC primary plus F1/precision/recall/Brier — not accuracy alone.
- Extra rigor: overfit-tiny-subset and label-shuffle sanity checks, both passing.
- Same (zero) tuning budget for both models — symmetric and honest.
- Limitation: a **single temporal split**; the ±std reflects model seed noise only (and LR's is exactly 0, deterministic), not split variation. No CV/walk-forward.

### Reproducibility — excellent
Seeds `[0,1,2,3,4]` fixed and logged, config + metrics written to `results/metrics.json`, dataset generation deterministic, and re-running produced identical output.

### Claims — mostly disciplined

However, limitations are unusually honest: explicitly flags single-split variance, no tuning, synthetic-data favoring LR's model class, only-5-seeds, and need for a paired test. No claim exceeds what the code measured; sanity figures match `metrics.json`.
