# Experiments Ledger

Append-only log of benchmark runs. Newest first. One entry per run.

**Division of labor (so this never drifts):** the human writes the *judgment* — hypothesis, what changed, the honest conclusion, next step. The *numbers* come straight from `analyze.py`; never hand-edit a metric. Regenerate any result block with:

```bash
python3 analyze.py report runs/review/<review_id> --format markdown   # table for this file
python3 analyze.py report runs/review/<review_id> --format csv         # import into W&B / MLflow / a sheet
```

Failed and null results stay in the ledger. Deleting an entry because it disappointed is exactly the fabrication-by-omission the skill forbids.

## 2026-06-15 — exp-004: harder prompt with a disguised leak (v2)

- **Hypothesis (from exp-003's next step):** v1's leak (`account_status`) was caught on name alone, leaving no headroom. A leak disguised as a plausible feature (`days_since_last_login`, target-derived, honest-feature AUC ~0.73 vs ~0.95 with the leak) will make the baseline slip and let the skill show an effect.
- **Setup:** codegen `20260615_084306_37526` → review `20260615_102920_51479`. Codegen **Sonnet** (matches exp-002 so prompt difficulty is the only change vs that run), review Opus with the **v2 rubric**, 10 repeats per arm, prompt `ml-experiment-v2`, fixture `make_dataset_v2.py`.
- **What varied vs exp-002:** dataset + prompt (v1 → v2 disguised leak). Model, arms, reviewer, repeats fixed.

**Result** (generated by `analyze.py report ... --format markdown`):

| Arm | n | Weighted mean | sd | leakage prevention | methodological validity | reproducibility | claims discipline | executability | code quality | Verdicts |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `rigor_only` | 10 | 92.9 | 1.8 | 96.1 | 88.7 | 93.7 | 89.5 | 97.3 | 90.7 | excellent 10 |
| `skills_off` | 10 | 91.4 | 2.2 | 96.0 | 84.4 | 93.3 | 86.0 | 97.5 | 90.0 | excellent 9, good 1 |

- `rigor_only` − `skills_off`: diff +1.5, Mann-Whitney z=1.40, p=0.16

- **Conclusion: first positive direction (+1.5) for the skill across all four experiments, but still not significant (p=0.16).** Honest reading of where it came from:
  - **The disguise failed against Sonnet.** Both arms dropped/justified `days_since_last_login` in 10/10 runs (verified from leakage_findings). Leakage prevention is a dead tie (96.1 vs 96.0). Sonnet reasons about *when* the value is known even without the skill, so the intended leakage headroom never materialized.
  - **The skill's edge came from elsewhere:** methodological_validity (+4.3) and claims_discipline (+3.5) — the skill arm tuned both models more even-handedly and wrote more cautious reports. This is the first time the skill's emphasis shows up consistently in the scores, and it flipped the overall sign positive.
  - **Still inside the noise.** +1.5 with sd ~2 at n=10 gives p=0.16. Directionally encouraging, not a detected effect. Per the skill's own claims discipline: no winner claimed.
- **Next step (exp-005):** the disguise needs a weaker model to bite. Run **Haiku on v2** — Haiku is the model most likely to miss the "when is this value known" inference and actually use the leak, finally creating leakage-prevention headroom. Separately, bump n (≥30) to tighten the interval around the +1.5 methodological/claims effect, and consider the objective AST-based leak check (does the code put the leaky column in the model's feature matrix?) to measure leakage deterministically instead of via reviewer score.

## 2026-06-12 — exp-003: capability ladder top — Opus codegen

- **Harness note:** one review (`rigor_only/run_04`) produced invalid JSON on the first attempt and was automatically retried to a valid result (`attempts=2` in the manifest) — the run-time validation guard working as designed.

- **Conclusion: exact tie (93.6 vs 93.6, p=0.47).** 19 of 20 runs rated `excellent`. The ceiling reading from exp-002 is confirmed at the top of the ladder: Opus saturates this prompt with or without the skill.
- **Ladder summary (exp-001/002/003, same prompt, arms, reviewer, n=10 each):**

The consistent secondary signal is that the skill arm has equal-or-higher variance at every level. The prompt — whose traps every model from Haiku up mostly catches — is the binding constraint, not capability.
- **Next step (exp-004):** a harder prompt (`ml-experiment-v2`): leakage through a plausible engineered feature (not an obviously target-named column), so the baseline cannot trivially catch it. That is now the only credible way to give the skill headroom to show an effect on this benchmark.

## 2026-06-12 — exp-002: does a stronger codegen model turn the skill's effect positive?

- **Setup:** codegen `20260612_113729_54901` → review `20260612_162643_87738`. Codegen model **Sonnet** (only change vs exp-001), review model Opus, 10 repeats per arm, prompt `ml-experiment-v1`.

- **Conclusion: hypothesis not supported — still no detectable difference (p=0.65), and the gap closed rather than turned positive.** Sonnet lifted both arms far above the Haiku runs (≈+7–10 weighted points) and removed exp-001's failure modes entirely: no `poor` runs, no catastrophic leak, both arms' sd tightened to ~3. After that, the higher-leverage change is a harder prompt: leakage through a plausible engineered feature rather than an obviously target-named column.

## 2026-06-12 — exp-001: does the skill beat the no-skill baseline?

- **Hypothesis:** With the `experiment-as-argument` skill loaded, a coding agent produces a more rigorous ML experiment (fewer leaks, honest claims, repeatable results) than the same agent with no skill.
- **Setup:** codegen `20260612_083306_91273` → review `20260612_092725_69742`. Codegen model Haiku, review model Opus, 10 repeats per arm. Prompt `ml-experiment-v1`. Arms: `skills_off`, `rigor_only`.
- **What varied:** only the workspace `.claude/skills/` directory (skill present vs absent). Everything else held fixed.

**Result** (generated by `analyze.py report ... --format markdown`):

| Arm | n | Weighted mean | sd | leakage prevention | methodological validity | reproducibility | claims discipline | executability | code quality | Verdicts |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `rigor_only` | 10 | 78.9 | 12.2 | 82.2 | 70.4 | 83.3 | 67.1 | 94.7 | 75.2 | good 9, poor 1 |
| `skills_off` | 10 | 81.6 | 4.6 | 87.4 | 71.4 | 89.0 | 67.3 | 94.3 | 78.7 | good 10 |

- `rigor_only` − `skills_off`: diff -2.7, Mann-Whitney z=0.08, p=0.94

- **Conclusion: no detectable difference (p=0.94).** Per the skill's own claims discipline, the 2.7-point gap is well inside the noise (skill-arm sd alone is 12.2), so no winner is claimed. Drilling in: the Haiku baseline already caught the headline target-leak trap in nearly every run (leakage 87.4, all 10 `good`), leaving little headroom; the skill arm's variance came from a single `poor` run (run_09) that used `account_status` directly as a feature. Excluding that one run, the skill arm is 82.6 ± 4.2 vs baseline 81.6 ± 4.6 — still inside the noise. Only `reproducibility` differed significantly (88.0 vs 83.5, p=0.02), *favoring the baseline*: the skill prompts more sanity-check code, which a weak model often implements incorrectly (e.g. an unseeded, no-op label-shuffle test), enlarging the defect surface.
- **Next step (exp-002):** rerun with a stronger codegen model (Sonnet) to test whether the skill's effect turns positive once the model can correctly execute the extra checks it prescribes. Separately, design a prompt whose leak is non-obvious (leakage through a plausible engineered feature, not an obviously target-named column) so the baseline cannot trivially catch it.
