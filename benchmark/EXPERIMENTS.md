# Experiments Ledger

Append-only log of benchmark runs. Newest first. One entry per run.

**Division of labor (so this never drifts):** the human writes the *judgment* — hypothesis, what changed, the honest conclusion, next step. The *numbers* come straight from `analyze.py`; never hand-edit a metric. Regenerate any result block with:

```bash
python3 analyze.py report runs/review/<review_id> --format markdown   # table for this file
python3 analyze.py report runs/review/<review_id> --format csv         # import into W&B / MLflow / a sheet
```

Failed and null results stay in the ledger. Deleting an entry because it disappointed is exactly the fabrication-by-omission the skill forbids.

## 2026-06-16 — exp-006: strengthened leak rule (timing test) on Haiku + v2

- **Change under test:** the "hunt target leakage" rule was rewritten from "drop OR justify" to a mechanical **timing test** ("at prediction time, is this value already final? if it moves as the outcome unfolds, drop it — a plausible name is not a justification"). This targets exp-005 run_06, the one genuine leak, where the agent rationalized `days_since_last_login` as "valid (recorded pre-prediction)."
- **Setup:** codegen `20260616_090932_6161` → review `20260616_094442_59447`. Codegen Haiku, review Opus + v2 rubric, `rigor_only` arm, 10 repeats, prompt/fixture v2. Compared against exp-005's already-collected `rigor_only` (old skill) and `skills_off` (baseline).

**Result** (generated by `analyze.py report ... --format markdown`):

| Arm | n | Weighted mean | sd | leakage prevention | methodological validity | reproducibility | claims discipline | executability | code quality | Verdicts |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `rigor_only` | 10 | 84.1 | 4.4 | 90.5 | 76.7 | 88.0 | 69.9 | 95.9 | 80.4 | good 7, excellent 3 |

Comparison (different batches — see caveat):

| Arm | weighted mean | sd | leakage | main-pipeline leak | poor verdicts |
| --- | ---: | ---: | ---: | ---: | ---: |
| exp-005 `rigor_only` (old skill) | 79.9 | 10.7 | 83.4 | 1/10 | 1 |
| exp-006 `rigor_only` (new skill) | **84.1** | **4.4** | **90.5** | **0/10** | **0** |
| exp-005 `skills_off` (baseline) | 80.8 | 6.6 | 91.8 | 0/10 | 0 |

- **Conclusion: the strengthened rule improved every weakness exp-005 exposed, and is the first skill arm to top the baseline on weighted mean (84.1 vs 80.8).** Main-pipeline leak 1/10 → 0/10 (verified by reading the code, not a checker); leakage subscore +7.1 (now level with the baseline's 91.8); variance halved (sd 10.7 → 4.4); the lone `poor` verdict gone. The timing-test framing removed the rationalization path that produced run_06.
- **Caveat (do not overclaim):** exp-006 `rigor_only` and exp-005's arms are **separate codegen batches**, not a single randomized run, so part of the gain could be batch-to-batch variation rather than the rule change. No significance test is valid across batches. This is a strong, mechanistically-explained directional result, not a confirmed effect.
- **Next step (exp-007):** the clean test is a single batch with three arms — `skills_off`, `rigor_only` (current skill), and ideally the old skill — at n ≥ 30, Haiku + v2, so leak rate and weighted mean can be compared within one run with a real interval. Only then can "the skill helps on weak models" be claimed rather than suggested.

## 2026-06-16 — exp-005 CORRECTION: the "skill leaks 5×" conclusion was wrong

The exp-005 entry below claimed the skill arm leaked the disguised feature 5/10 vs the baseline's 1/10, from `analyze.py leak-check`. **That conclusion was an artifact of a flawed tool and is retracted.** On re-reading every flagged workspace's code:

- 4 of the 5 `rigor_only` "leaks" (run_04, 05, 07, 08) and the 1 `skills_off` "leak" (run_08) were **leakage-ceiling demos, not real leaks**: the main pipeline dropped `days_since_last_login` and used it only in a separate analysis that intentionally trains *with* the leak to show how much it inflates AUC — exactly the skill's "leakage ceiling" sanity check, a good behavior. `leak-check` scanned all code and counted those demo `features=[...]` lines as real usage.
- Only **rigor_only/run_06** is a genuine main-pipeline leak (it judged the column "valid (recorded pre-prediction)" and kept it).

**Corrected main-pipeline leak rate: `skills_off` 0/10, `rigor_only` 1/10** — a one-run difference, well within noise, consistent with the reviewer's null (−1.0, p=0.50). The skill did **not** increase leakage; if anything it more often induced the leakage-ceiling demo.

Consequences:
- The five-experiment verdict is **null everywhere, not "harmful on weak models."** Corrected in README.
- `leak-check` is **removed**. After two false-positive patches it still couldn't tell an intentional leak demo from a real leak — and because the skill induces those demos, it was systematically biased against the `rigor_only` arm. A static syntax check ("is the column in a `features=` list?") cannot capture the domain invariant ("does the *main* model use it?").
- My exp-005 claim that "the objective check beat the reviewer" was backwards: the checker was wrong and reading the code was right. That is the skill's own thesis — when a measurement contradicts the theory, rebuild the theory; a narrow automated metric is not a substitute for understanding the program.

The original (incorrect) entry is kept below unedited, per the ledger's append-only rule.

## 2026-06-15 — exp-005: make the disguised leak bite (Haiku + v2)  *(superseded — see correction above)*

- **Hypothesis (from exp-004's next step):** the v2 disguise didn't bite on Sonnet (both arms caught it 10/10). A weaker model should miss the "when is this value known" inference and actually use the leak, creating leakage-prevention headroom where the skill can finally help.
- **Setup:** codegen `20260615_142410_77539` → review `20260615_153024_65379`. Codegen **Haiku**, review Opus with v2 rubric, 10 repeats per arm, prompt `ml-experiment-v2`, fixture `make_dataset_v2.py`. (`rigor_only/run_02` was regenerated after a retry-guard bug let it through empty; see the harness fix.)

**Result — reviewer scores** (generated by `analyze.py report ... --format markdown`):

| Arm | n | Weighted mean | sd | leakage prevention | methodological validity | reproducibility | claims discipline | executability | code quality | Verdicts |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `rigor_only` | 10 | 79.9 | 10.7 | 83.4 | 68.1 | 85.9 | 65.6 | 96.1 | 82.7 | good 9, poor 1 |
| `skills_off` | 10 | 80.8 | 6.6 | 91.8 | 70.3 | 81.9 | 67.8 | 89.0 | 80.2 | good 7, mixed 1, excellent 2 |

- `rigor_only` − `skills_off`: diff -1.0, Mann-Whitney z=0.68, p=0.50

**Result — objective leak-check** (`analyze.py leak-check`, reviewer-independent; all `leaked` verdicts hand-verified as real `features=[... days_since_last_login ...]` usage):

| Arm | leaked | handled |
| --- | ---: | ---: |
| `rigor_only` | **5/10** | 5 |
| `skills_off` | **1/10** | 9 |

- **Conclusion: the disguise finally bit — and the skill made things worse, not better.** Two findings, the second only visible because of the objective check:
  1. **The leak bit on Haiku.** The baseline leaked 1/10 here vs 0/10 on Sonnet (exp-004): a weaker model does miss the "recorded after the outcome" inference, so v2 created real headroom. Confirmed the exp-004 next-step reasoning.
  2. **The skill arm leaked 5× as often (5/10 vs 1/10).** This is the opposite of the skill's purpose. Reviewer weighted means hide it (−1.0, p=0.50) because the skill arm scored higher on executability/reproducibility, diluting the leakage gap; the objective leak-check (and the leakage_prevention subscore, 83.4 vs 91.8) expose it. The skill arm also had higher variance (sd 10.7 vs 6.6) and the only `poor` verdict.
- **Interpretation:** on a weak model, the skill backfires on the very failure it targets. The likely mechanism is the recurring one from exp-001: the skill pushes Haiku to do *more* (more features engineered, more pipeline), and a model that can't carry that load ends up pulling the leaky column into the feature matrix rather than reasoning it out. "More rigor instructions" ≠ "more rigor" when the model can't execute them.
- **Cross-experiment verdict (5 experiments):** the skill has not produced a detectable score win in any setting; on a strong model it's absorbed by the ceiling, and on a weak model it actively increases leakage and variance. The one positive signal (exp-004 methodology/claims, +1.5) was not significant and not about leakage.
- **Next step (exp-006):** this is now a skill-content question, not a measurement one. Read the 5 `rigor_only` leak findings to learn *why* the skill leads Haiku into the leak, then revise the skill (the "hunt target leakage" rule may need a concrete "drop anything recorded at/after the outcome" checklist the weak model can follow mechanically) and re-run Haiku+v2 to test whether the revision removes the backfire. Larger n (≥30) would also tighten the leak-rate difference.

> Methodology note: exp-005 is where the objective `leak-check` earned its place — the reviewer's weighted mean said "no difference," but the leak rate said the skill arm was clearly worse. Measuring the invariant directly beat trusting an aggregate score, which is the skill's own thesis applied to its own benchmark.

## 2026-06-15 — exp-004: harder prompt with a disguised leak (v2)

- **Hypothesis (from exp-003's next step):** v1's leak (`account_status`) was caught on name alone, leaving no headroom. A leak disguised as a plausible feature (`days_since_last_login`, target-derived, honest-feature AUC ~0.73 vs ~0.95 with the leak) will make the baseline slip and let the skill show an effect.
- **Setup:** codegen `20260615_084306_37526` → review `20260615_102920_51479`. Codegen **Sonnet** (matches exp-002 so prompt difficulty is the only change vs that run), review Opus with the **v2 rubric**, 10 repeats per arm, prompt `ml-experiment-v2`, fixture `make_dataset_v2.py`.
- **What varied vs exp-002:** dataset + prompt (v1 → v2 disguised leak). Model, arms, reviewer, repeats fixed.

**Result** (generated by `analyze.py report ... --format markdown`):

| Arm | n | Weighted mean | sd | leakage prevention | methodological validity | reproducibility | claims discipline | executability | code quality | Verdicts |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `rigor_only` | 10 | 92.9 | 1.8 | 96.1 | 88.7 | 93.7 | 89.5 | 97.3 | 90.7 | excellent 10 |
| `skills_off` | 10 | 91.4 | 2.2 | 96.0 | 84.4 | 93.3 | 86.0 | 97.5 | 90.0 | excellent 9, good 1 |

- `rigor_only` − `skills_off`: diff +1.5, Mann-Whitney z=1.40, p=0.16

- **Conclusion: first positive direction (+1.5) for the skill across all four experiments, but still not significant (p=0.16).** Honest reading of where it came from:
  - **The disguise failed against Sonnet.** Both arms dropped/justified `days_since_last_login` in 10/10 runs (verified from leakage_findings). Leakage prevention is a dead tie (96.1 vs 96.0). Sonnet reasons about *when* the value is known even without the skill, so the intended leakage headroom never materialized.
  - **The skill's edge came from elsewhere:** methodological_validity (+4.3) and claims_discipline (+3.5) — the skill arm tuned both models more even-handedly and wrote more cautious reports. This is the first time the skill's emphasis shows up consistently in the scores, and it flipped the overall sign positive.
  - **Still inside the noise.** +1.5 with sd ~2 at n=10 gives p=0.16. Directionally encouraging, not a detected effect. Per the skill's own claims discipline: no winner claimed.
- **Next step (exp-005):** the disguise needs a weaker model to bite. Run **Haiku on v2** — Haiku is the model most likely to miss the "when is this value known" inference and actually use the leak, finally creating leakage-prevention headroom. Separately, bump n (≥30) to tighten the interval around the +1.5 methodological/claims effect, and consider the objective AST-based leak check (does the code put the leaky column in the model's feature matrix?) to measure leakage deterministically instead of via reviewer score.

## 2026-06-12 — exp-001: does the skill beat the no-skill baseline?

- **Hypothesis:** With the `experiment-as-argument` skill loaded, a coding agent produces a more rigorous ML experiment (fewer leaks, honest claims, repeatable results) than the same agent with no skill.
- **Setup:** codegen `20260612_083306_91273` → review `20260612_092725_69742`. Codegen model Haiku, review model Opus, 10 repeats per arm. Prompt `ml-experiment-v1`. Arms: `skills_off`, `rigor_only`.
- **What varied:** only the workspace `.claude/skills/` directory (skill present vs absent). Everything else held fixed.

**Result** (generated by `analyze.py report ... --format markdown`):

| Arm | n | Weighted mean | sd | leakage prevention | methodological validity | reproducibility | claims discipline | executability | code quality | Verdicts |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `rigor_only` | 10 | 78.9 | 12.2 | 82.2 | 70.4 | 83.3 | 67.1 | 94.7 | 75.2 | good 9, poor 1 |
| `skills_off` | 10 | 81.6 | 4.6 | 87.4 | 71.4 | 89.0 | 67.3 | 94.3 | 78.7 | good 10 |

- `rigor_only` − `skills_off`: diff -2.7, Mann-Whitney z=0.08, p=0.94

- **Conclusion: no detectable difference (p=0.94).** Per the skill's own claims discipline, the 2.7-point gap is well inside the noise (skill-arm sd alone is 12.2), so no winner is claimed. Drilling in: the Haiku baseline already caught the headline target-leak trap in nearly every run (leakage 87.4, all 10 `good`), leaving little headroom; the skill arm's variance came from a single `poor` run (run_09) that used `account_status` directly as a feature. Excluding that one run, the skill arm is 82.6 ± 4.2 vs baseline 81.6 ± 4.6 — still inside the noise. Only `reproducibility` differed significantly (88.0 vs 83.5, p=0.02), *favoring the baseline*: the skill prompts more sanity-check code, which a weak model often implements incorrectly (e.g. an unseeded, no-op label-shuffle test), enlarging the defect surface.
- **Next step (exp-002):** rerun with a stronger codegen model (Sonnet) to test whether the skill's effect turns positive once the model can correctly execute the extra checks it prescribes. Separately, design a prompt whose leak is non-obvious (leakage through a plausible engineered feature, not an obviously target-named column) so the baseline cannot trivially catch it.
